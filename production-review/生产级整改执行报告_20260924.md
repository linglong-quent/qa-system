### 1.3 模拟 Redis 实例定性（`fed15044`）—— 长期误判的澄清

`linglong-redis-a` 一直被当作"未部署的容器"（prometheus 永久 down、health_check 必然失败、文档三实例只见两个容器）。

**实测结论：模拟实例存在，是宿主原生 Memurai 4.1.2**（Redis 7.2.5 兼容），监听 6380：

```
memurai_edition: Memurai Developer     memurai_version: 4.1.2
redis_version:   7.2.5                 tcp_port:        6380
```

- 容器经 `host.docker.internal:6380` 可达，`DBSIZE=2`，无口令 `NOAUTH`
- `config/paths.py:341` 本就按此区分（`windows→127.0.0.1` / 容器内→`linglong-redis-a`）
  —— **配置是对的，是运维侧把"宿主原生"当成了"容器未部署"**
- **口令一致性**：三实例共用同一口令，K3 对 6379/6381/6380 均 PONG

**两处修复**：
1. `health_check.py` 改为宿主侧裸 RESP 探测。原实现两缺陷叠加、靠"无条件打 [OK]"掩盖：
   `docker exec` 查不存在的容器名；且口令写成在容器内展开 `"$REDIS_PASSWORD"`，
   而实测 **redis 容器内该变量为空**（`len=0`）。新实现无第三方依赖、口令只走 socket 不落 argv。
   实测：三实例 PONG；错口令与端口不通均如实失败。
2. compose 补 `redis-exporter-sim`（经 `host.docker.internal:6380` 取数）。
   prometheus 早有该 job 却**从来没有对应 exporter**。实测 `redis_up 1`，
   三个 redis 靶子**全部 up**。
